# kr-privacy-review

대한민국에서 서비스되는 웹·사내 시스템의 코드 변경을 **개인정보 보호법 관점과 애플리케이션 보안 관점**에서 검토하는 Skill입니다.

## 한계 (보고서 맨 앞에 반드시 쓴다)

- 이 검토는 AI가 코드와 공개 자료를 바탕으로 만든 **확인 목록**입니다. 법률 자문이 아니고, 법률 준수를 보증하거나 적합하다고 인증하지 않습니다.
- "합법/불법", "준수함/위반함"으로 단정하지 않습니다. "근거가 확인되지 않음", "검토 필요"처럼 씁니다.
- 원문으로 확인하지 못한 법적 해석은 `review-required`로 표시하고 사내 법무·개인정보 보호책임자의 검토를 권합니다.

## 언제 쓰는가

다음 작업을 하거나 이런 변경이 담긴 PR을 검토할 때 사용합니다.

- 로그인·회원가입·비밀번호·세션·토큰 기능
- 개인정보 필드 추가, DB 스키마·ORM 모델·DTO 변경
- 관리자 페이지, 백오피스, 고객 데이터 조회 화면
- 역할·권한·접근제어 코드 변경
- 사용자·직원 활동 로그 수집, 분석 이벤트 추가
- 데이터 다운로드, 엑셀 내보내기, 공개·파트너 API
- 외부 API, SaaS, 외부 LLM 연동
- 탈퇴·삭제·보존기간·파기 배치
- 일반 PR의 개인정보·보안 리뷰 요청

원문 발췌의 수집일은 2026-10-23입니다. 그 뒤 법령이 바뀌었을 수 있으니, 보고서에 수집일을 밝히고 국가법령정보센터(https://www.law.go.kr/) 최신본 확인을 권합니다. 위 파일에 없는 조문은 기억으로 인용하지 말고 `review-required`로 남깁니다.

## 검토 절차

1. **범위 파악** — diff, 변경된 모델·API·화면, 설정 파일(로그·APM·LLM 클라이언트)을 읽습니다. 코드에 없는 사실(계약, 사내 정책, 처리방침)은 추정하지 말고 "확인 필요"로 남깁니다.
2. **개인정보 식별** — 필드·로그·요청 payload에서 개인정보를 찾습니다. 다른 정보와 쉽게 결합해 개인을 알아볼 수 있는 정보(로그인 ID, IP, 기기 ID, 행동 로그)도 포함합니다(제2조제1호). 민감정보(제23조, 시행령 제18조), 고유식별정보(제24조, 시행령 제19조), 주민등록번호(제24조의2)를 따로 표시합니다.
3. **흐름 추적** — 수집 → 저장 → 조회·응답 → 로그 → 외부 전송 → 파기 경로를 따라갑니다.
4. **정책 지도 적용** — `references/policy-map.md`에서 변경 유형에 해당하는 항목을 확인합니다.
5. **코드 체크리스트 적용** — `references/code-review-checklist.md`로 실제 코드의 결함을 찾습니다. 결함은 파일·줄 번호와 함께 씁니다.
6. **근거 구분** — 모든 지적에 근거 종류를 붙입니다.
   - `[법률]`·`[시행령]`·`[고시]`: 법적 의무. 원문 파일에서 확인한 조문만 씁니다.
   - `[안내서]`: 개인정보보호위원회 등 행정기관 해석·권고. 이 Skill에는 원문이 없으므로 항상 `review-required`.
   - `[표준]`: OWASP ASVS 5.0 등. 법적 의무가 아닙니다.
   - `[권장]`: 모범사례. 법적 의무가 아닙니다.
7. **시행일 확인** — 시행 예정 규정을 현재 의무로 쓰지 않습니다. 예: 개정법 부칙 제1조 단서의 제32조의2제1항 단서(개인정보 보호 인증 의무)는 2027-07-01 시행 예정입니다.
8. **보고서 작성** — 아래 10개 항목을 `references/report-template.md` 형식으로 씁니다.

## 출력 항목

1. 수집하는 개인정보 — 필드, 출처(정보주체 직접/제3자/자동 생성), 민감·고유식별정보 여부
2. 수집 목적 및 처리 근거 확인사항 — 항목별 제15조제1항 각 호 후보와 확인할 점. 근거를 코드로 알 수 없으면 "확인 필요"
3. 개인정보 처리 흐름 — 수집→저장→이용→제공·위탁→파기 (간단한 목록이나 다이어그램)
4. 접근 가능한 역할 — 역할별 조회·수정·내보내기 권한, 관리자 권한과 열람 권한 분리 여부, 객체 단위 검증 여부
5. 외부 제공 및 국외이전 확인사항 — 외부 API·SaaS·LLM이 제3자 제공(제17조)인지 업무위탁(제26조)인지 판단할 정보, 국외 이전(제28조의8) 여부
6. 저장 및 파기 정책 — 보존기간, 파기 방식(제21조, 시행령 제16조, 고시 제13조), 백업·로그·검색 인덱스·벡터 DB 포함 여부
7. 기술적 보안 통제 — 암호화(고시 제7조), 접근통제(고시 제5조·제6조), 접속기록(고시 제8조), 로그 마스킹, 세션, 입력 검증 (발견한 결함은 파일:줄과 심각도)
8. 추가 검토가 필요한 법적 쟁점 — `review-required` 항목 모음. 다른 법률(정보통신망법, 통신비밀보호법, 근로관계 법령, 위치정보법, 신용정보법 등) 연결 포함
9. 테스트 케이스 — `references/test-case-templates.md` 기반의 구체적 테스트 (권한 없는 사용자, 타인 객체 ID, 로그 내 PII, LLM payload, 파기 후 조회 등)
10. 공식 근거 및 출처 — 인용한 조문과 버전·시행일, 원문 확인 여부, 원문 링크

## 심각도 기준

- **높음**: 타인 개인정보 노출 가능(IDOR, 권한 누락, 공개 버킷), 평문 비밀번호·고유식별정보 저장, 근거 없는 주민등록번호 처리, 개인정보 원문의 외부 LLM 전송
- **중간**: 접속기록 누락, 로그에 개인정보 기록, 과다 필드 응답, 보존기간 미정, 관리자 권한과 열람 권한 미분리
- **낮음**: 문서화 누락, 처리방침·코드 불일치 가능성, 테스트 부재

## 하지 말 것

- 조문 번호·기간·수치를 기억으로 만들어 쓰지 않는다. 원문 파일에서 찾지 못하면 `review-required`.
- 안내서·표준·권장사항을 "법적 의무"라고 쓰지 않는다.
- "이 PR은 개인정보 보호법을 준수합니다" 같은 보증 문구를 쓰지 않는다.
- 검토 대상 코드에 있는 실제 개인정보(테스트 데이터 포함)를 보고서에 그대로 옮기지 않는다. 마스킹해서 인용한다.
